# 人物角色拆分：主角（誰的行程）× 相關人物（拜訪／參與／對象）

狀態：草案（待確認範圍後實作）
日期：2026-09-30

## 問題與情境

現在事件的「人物」只有一種，把「這是誰的行程」和「見到／一起做的人」混在一起。
真實情境：**大人（Peggy）幫小孩記行程，但實際活動的是小孩**。例如「數學家教課」——
實際上課的是小明，老師是陳老師。用單一人物欄無法區分，導致：

- 空檔要看「小明的空閒」得靠「沒掛人物＝本人」的 hack，無法乾淨表達。
- 財務「依老師」統計與「這個小孩幾個活動」混在一起。

## 設計：人物分兩種角色

| 角色 | 命名 | 意義 | 典型 | 驅動 |
|---|---|---|---|---|
| subject | **主角**（誰的行程） | 這筆行程是誰的／實際在做的人 | 小明、小美、本人 | 空檔聚焦、活動次數統計 |
| participant | **相關人物**（拜訪·參與·對象） | 去見／一起做／服務你的人 | 陳老師、王執行長、阿姨、醫師 | 財務依老師（現有）、見了誰幾次 |

命名定案：**主角** / **相關人物**（UI 各附小字副標）。備選曾考慮「對象/參與者」「誰的行程/拜訪對象」，因「對象」易與相關人物混淆而不採。

「本人（Peggy）」= **未指定主角**的行程（沿用目前 self 語意），不必另建人物；
若使用者想明確化，也可建一個 is_family 的「本人」人物。

## 資料模型

```sql
-- 事件↔人物 加角色（預設 participant，向下相容）
alter table public.event_contacts
  add column role text not null default 'participant'
    check (role in ('subject','participant'));

-- 人物標記「可當主角」（家人／本人），用來把兩個選單分區
alter table public.contacts
  add column is_family boolean not null default false;
```

- 現有 event_contacts 全部視為 participant（老師/客戶等），role 用預設值即可，**免 backfill**。
- PK 維持 (event_id, contact_id)；role 為屬性。同一人同一事件不重複掛。

## 各處影響（實作清單）

1. **事件表單 event-modal**：由單一「人物」→ 兩個多選：
   - 主角（誰的行程）：清單以 `is_family` 人物優先。
   - 相關人物（拜訪/參與）：即現有「人物」欄。
2. **事件資料 client（events.ts / types）**：查詢帶回 role，CalEvent 由 `contactNames`
   拆成 `subjectNames` / `participantNames`（保留相容欄位供顯示）。
3. **空檔聚焦（calendar-view）**：聚焦對象新增「主角」區（`subj:<contactId>`），
   本人＝未指定主角。參與/對象人物是否也可聚焦待定（預設不放，避免雜訊）。
4. **財務自動帶入（event-modal）**：找有預設收費的老師時，改掃 **相關人物**（participant）。
5. **報表**：新增「依主角（誰的行程）」活動次數統計（可 Phase 2）。
6. **人物管理**：新增「家人／可當主角」勾選（設定 is_family）。
7. **語音/匯入**：帶入的人物預設為 participant。

## 家教課 × 費用（核心情境，務必想清楚）

一筆「數學家教課」：**主角＝小明**（實際上課、成本歸他）、**相關人物＝陳老師**
（收費對象、你付錢給他）。費用有兩個歸屬維度，別混：

| 維度 | 問題 | 資料來源 | 狀態 |
|---|---|---|---|
| 收費對象（付給誰） | 「付陳老師這月幾堂／多少」 | `finance_records.contact_id` = **相關人物(老師)** | 現有，沿用 |
| 成本歸屬（誰的花費） | 「小明這月家教費多少」 | 由 `finance_records.event_id` → 事件的**主角**推導 | 新增報表維度 |

**規則定案：**
1. 財務仍掛在**相關人物（老師）**——`finance_records.contact_id` 存老師，
   「依老師」統計、預設收費自動帶入都以老師為準（不變）。
2. **自動帶入改掃「相關人物」**：選到有預設收費的老師才帶金額（主角小孩沒有費率，
   本來就不會誤觸；但邏輯上明確只掃 participant）。
3. **儲存財務時 contact_id = 收費的相關人物**（目前是掃事件所有人物取第一個有費率者；
   拆分後改為只在 participant 中找）。
4. **「依小孩（主角）費用」報表**：用 finance_records join 事件的主角來分組，
   得到「小明 家教費 4 堂 6400／小美 才藝費 …」。屬 Phase 2。
5. **預繳帳戶**：`prepaid_accounts` 已有 `contact_id`(老師)＋`calendar_id`。
   若分類是按小孩分（小明分類），則「小明的陳老師預繳」＝該帳戶天然可表達；
   不需為主角另加欄位。若日後同一分類混多小孩，再評估加 subject。

**結論**：拆分角色**不改財務主鍵結構**（費用照掛老師），只是
（a）自動帶入與存檔改鎖定 participant、（b）多一個「依主角」的**讀取維度**（報表）。
風險低，且正好把「誰上課」與「付給誰」分乾淨。

## 分階段

- **Phase 1（核心可用）**：migration＋人物管理 is_family＋事件表單兩欄＋events 帶 role＋
  空檔聚焦支援主角。上線後即可「主角=小明」聚焦。
- **Phase 2（統計）**：報表「依主角」次數；財務自動帶入改掃相關人物（若 Phase 1 未併）。

## 風險 / 待確認

- 需 `npm run db:push` 套用 migration 到線上 Supabase（會動到正在測的庫）。
- 主角是否允許多位（例：兩個小孩一起的家庭活動）→ 採**多選**，通常填一位。
- 舊資料：目前掛的人物是否真的都是「相關人物」？若有些其實是主角，需人工調整
  （量少，先不自動判斷）。
