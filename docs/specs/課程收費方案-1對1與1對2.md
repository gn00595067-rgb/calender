# 課程收費方案：同一位老師 1 對 1／1 對 2 不同鐘點費

狀態：已實作 Phase 1＋2（2026-10-03），待套 migration 0008 後實測
日期：2026-10-03

## 問題與情境

同一位老師可能：
- **1 對 1** 只教小明，例如每小時 1,200。
- **1 對 2** 同時教小明＋小美，鐘點費不同，以「一堂總價」報價（兩人一起每小時 1,800）。
- 已確認：不會和別家小孩共上；同一位老師不同科目不會不同價。

現況的限制：
1. 每位老師只能設**一個**費率（`contacts.billing_mode` + `default_rate`），無法區分 1 對 1／1 對 2。
2. 金額只在「選到老師的那一刻」帶入一次，之後改主角人數或改上課時長都不會重算。
3. **統計 bug**：「依主角（誰的花費）」在一筆行程有兩位主角時，會把整筆金額**重複算給每個人**
   （小明 1,800＋小美 1,800＝3,600，實際只付 1,800）。不管本功能做不做，都要修。

不做會怎樣：1 對 2 的課每次都要手算金額再改；月底「這個月付陳老師多少」「小明的家教費花多少」都不準。

## 名詞

| 名詞 | 意義 |
|---|---|
| 收費方案（rate plan） | 老師底下的一組價目，例如「1對1」「1對2」「團班」 |
| 班型人數 headcount | 方案設定的上課人數（1、2、3…），用來自動挑方案 |
| 我家上課人數 | 這筆行程的**主角**數（小孩），沒有主角時視為 1 |

## 金額公式（唯一的真相）

```
金額 = billing_mode == hourly ? round(rate × 時數) : rate      （rate 一律是整堂總價）
```

| 例子 | 方案 | 時數 | 金額 |
|---|---|---|---|
| 小明 1對1 | 1對1、時薪 1,200 | 1.5 | 1,800 |
| 小明＋小美 1對2 | 1對2、時薪 1,800 | 1 | 1,800（統計時各分 900） |
| 小明 1對1 鋼琴 | 1對1、每堂 1,000 | — | 1,000 |

不做「每人計價」（rate_basis）：已確認不會和別家小孩共上，1對2 一律整堂總價。
日後若需要，再加 `rate_basis` 欄位（預設 total，向下相容）。

## 資料模型

### 新表：`contact_rate_plans`

```sql
create table public.contact_rate_plans (
  id           uuid primary key default gen_random_uuid(),
  owner_id     uuid not null references public.profiles (id) on delete cascade,
  contact_id   uuid not null references public.contacts (id) on delete cascade,
  label        text not null,                  -- 「1對1」「1對2」「團班」，可自訂
  headcount    int  not null default 1 check (headcount >= 1),
  billing_mode text not null check (billing_mode in ('fixed','hourly')),
  rate         numeric(12,0) not null check (rate >= 0),
  position     int  not null default 0,
  created_at   timestamptz not null default now()
);
create index contact_rate_plans_contact_idx on public.contact_rate_plans (contact_id, position);
-- RLS：比照 prepaid_accounts（擁有者可寫；被可檢視財務引用者可讀）
```

- 類別／收支方向／付款方式**留在 contacts**（`default_category_id` 等），同一老師的各方案共用，不重複設定。
- `contacts.billing_mode` / `default_rate` **保留不刪**（相容舊程式），由 migration 轉成一筆
  「1對1、headcount=1」方案；之後程式只讀方案表。

### `finance_records` 加欄位（存「當時」的快照）

```sql
alter table public.finance_records
  add column rate_plan_id  uuid references public.contact_rate_plans (id) on delete set null,
  add column lesson_label  text,   -- 快照：「1對2」（方案改名/封存後歷史仍正確）
  add column headcount     int,    -- 快照：班型人數
  add column learner_count int;    -- 快照：我家上課人數（分攤用）
```

- **一筆行程仍只對應一筆財務**（付給老師的那筆），維持現有「一行程一財務」結構，不拆成每個小孩一筆。
  理由：付錢的對象只有一位老師；拆筆會讓「依老師」對帳、預繳扣抵、編輯同步都變複雜。
- 分給小孩的金額在**統計時**用公式攤（見下方統計），不另外存。
- 金額 `amount` 仍是實際付款金額的真相源；方案只負責「算出建議值」，使用者可以手動改。

## 各處設計

### 1. 設定 › 人物（老師）

編輯老師時，原本的「計費方式＋金額」改成**收費方案清單**：

```
收費方案                                   [+ 新增方案]
┌──────────────────────────────────────────┐
│ 1對1   時薪 1,200 / 小時                  ✎ 🗄 │
│ 1對2   時薪 1,800 / 小時                  ✎ 🗄 │
└──────────────────────────────────────────┘
預設類別 [家教費 ▾]  付款方式 [月結 ▾]  方向 [支出 ▾]
```

新增／編輯方案的欄位：名稱（快選鈕：1對1／1對2／1對3／自訂）、人數、計費（固定每堂／時薪）、
金額（整堂總價）。

- 人物列表顯示摘要：「1對1 1,200/時 · 1對2 1,800/時」。
- **不做封存**：方案可以直接刪除／改價，歷史財務存有名稱快照與當時金額，不受影響
  （rate_plan_id 會 set null）。實作時判斷封存是多餘的複雜度。
- UX 防呆：同一老師兩個未封存方案人數相同時提示「新增行程時會預設挑第一個」。

### 2. 新增／編輯行程（event-modal）

選了**相關人物＝有方案的老師**後，財務區多一列「上課形式」：

```
主角      [小明 ×] [小美 ×]
相關人物  [陳老師 ×]
─── 財務 ───────────────────────────
上課形式  ( 1對1 )  [ 1對2 ✓ ]        ← 依主角人數自動選，可手動切
金額      1,800     依方案：時薪 1,800 × 1 小時
類別 家教費   付款 月結   □ 已結清
```

**自動挑方案規則**（依序）：
1. 老師未封存方案中，`headcount == 我家上課人數` 的第一個；
2. 沒有完全相符 → headcount 最接近且 ≥ 人數的；
3. 還是沒有 → 第一個方案，並顯示提示。

**自動重算**（修正「只帶入一次」）：
- 換方案、改主角人數、改時長（時薪制）→ 依公式重算金額。
- 使用者**手動改過金額**後就不再自動覆蓋，改成顯示：「依方案應為 2,700 ［套用］」。
- 編輯舊行程時沿用已存的金額，不自動重算；只有使用者改了上述欄位才出現［套用］提示。

**提示（不阻擋）**：
- 選 1對2 但主角只有一位 →「1對2 只選了 1 位小孩，要不要補上另一位？」
- 主角 2 位但老師只有 1對1 方案 →「陳老師沒有 1對2 方案，金額先用 1對1 計算」＋［去設定方案］連結。

重複行程：每一堂都用同一個方案與公式產生財務（沿用現有逐堂建立 finance_records 的邏輯）。

### 3. 行事曆顯示

- **行程詳情**：財務列顯示「陳老師 · 1對2 · 1,800（小明、小美 各 900）」。
- **兩行卡片**（週／日／當天面板）第二行：「陳老師 · 1對2 · 小明、小美」。
- **月曆 chip**：空間不足，不加。
- 空檔聚焦：1對2 行程本來就掛兩位主角，兩個小孩的空檔都會被佔用，不用改。

### 4. 統計（reports）

**分攤規則**：一筆財務的金額，平均分給它的主角（餘數給第一位）。
分攤一律依**當下的主角名單**（要知道分給誰，名單是唯一來源）；`learner_count` 只當紀錄保存。

| 區塊 | 改動 |
|---|---|
| 依主角（誰的花費） | **修重複計算**：每人拿 `amount / 主角數`；堂數每人各 +1 |
| 依老師／對象 | 每位老師底下再依上課形式分小計：「1對1 6 堂 7,200 · 1對2 4 堂 7,200」 |
| 匯出 CSV | 加「上課形式」「班型人數」「我家人數」「每人分攤」欄 |
| 預繳帳戶 | 1對2 一堂從帳戶扣「整筆金額」、堂數算 1 堂（老師上了一堂） |

不新增獨立的「依上課形式」區塊；放在老師底下就夠了，避免報表膨脹。

## 已確認（2026-10-03）

1. 1對2 報價＝**一堂總價** → 不做每人計價。
2. **不會**和別家小孩共上 → 「我家上課人數」＝主角數，方案人數即可自動挑。
3. 1對2 預繳＝**一個帳戶一起扣** → 沿用現有 prepaid_accounts，扣整筆、計 1 堂。
4. 同一老師不同科目**不會**不同價 → 不做科目維度。

## 風險

- 需 `npm run db:push` 套用 migration 到線上 Supabase；舊費率轉方案必須冪等、不會重複建立。
- event-modal 已近 1,000 行，財務區建議抽成 `finance-section.tsx` 再加功能，避免越改越難維護。
- 已存在的 1對2 行程（兩位主角）不會補快照；統計用當下的主角數分攤，結果仍正確。
