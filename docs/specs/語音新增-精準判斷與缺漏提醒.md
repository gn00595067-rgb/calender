# 語音新增：更準確的判斷＋資訊不足時的提醒

狀態：已實作（2026-10-03）
日期：2026-10-03

## 問題

語音一句話通常只講「什麼時間做什麼」，像「週二晚上哥哥桌球」。原本的解析只填標題、時間、地點、分類，
所以**主角、相關人物（老師）、標籤、司機、重複**都要事後手動補；漏補就會造成：
- 空檔聚焦、依主角統計少算（沒掛主角）；
- 老師沒掛 → 收費方案不會自動帶入，財務漏記；
- 需要司機卻沒標 → 司機時間表漏掉。

原本模型只拿到「分類清單」，不知道家裡有誰、老師是誰、過去這堂課通常怎麼排，判斷自然不準。

## 設計

### 1. 給模型足夠的脈絡（伺服器端查，不信任前端）

| 脈絡 | 來源 | 用途 |
|---|---|---|
| 人物清單（id、名字、稱謂、是否家人） | contacts | 「哥哥」「郭老師」對到人物；家人→主角、其他→相關人物 |
| 既有標籤 | tags | 優先沿用既有標籤，避免同義詞亂長 |
| **過去習慣**（近 120 天同名行程：次數、常見星期/時間/時長、分類、主角、老師、標籤、地點、是否要司機） | events＋關聯 | 「桌球」→ 自動補上郭老師、哥哥、運動、18:15–19:15、某球館 |
| 分類清單 | 前端（可編輯分類） | 挑分類 |

### 2. 模型輸出（結構化輸出，schema 保證可解析）

新增意圖回傳：分類、標題、整日、起訖、地點、重要、**主角 ids、相關人物 ids、標籤、是否要司機、重複規則（含星期）**，
外加：
- `fromHabit`：哪些欄位是依過去習慣推得（UI 標示「依過去紀錄帶入」，讓使用者知道不是他講的）；
- `assumptions`：模型做的假設（如「沒講時間，先用平常的 18:15」）；
- `questions`：缺了但重要的資訊，用一句溫和的中文問句（如「這是誰要上的課？」）；
- `unknownNames`：句子裡提到、但人物清單沒有的名字（如「林醫師」）。

### 3. 伺服器再檢查一遍（不完全依賴模型）

- id 不在清單一律丟掉；分類不在清單退回第一個。
- 依規則補提醒（與模型的去重）：
  - 沒有主角、但有家人 →「沒指定主角，會當成本人的行程；如果是小孩的活動請選主角」；
  - 要司機但沒地點 →「需要司機，但還沒有地點，司機會不知道要去哪」；
  - 標題像課程（課/班/家教/老師）但沒有相關人物 →「沒有選老師，收費方案不會自動帶入」；
  - 有沒對到的名字 →「〔林醫師〕不在人物清單，可在相關人物欄快速新增」。

### 4. 確認畫面（EventModal 頂端「語音解析」面板）

- 引用原句，方便對照有沒有聽錯；
- 三種提示：⚠ 需要確認（questions＋規則提醒，琥珀色）／✓ 依過去紀錄帶入（列出欄位）／ℹ 假設；
- 所有欄位都已預先帶入，使用者只需補 ⚠ 的部分再按儲存。仍然**不會**自動寫入資料庫。
- 選到老師後既有的收費方案自動帶入照常運作（語音帶入的相關人物會觸發）。

### 5. 模型

改用 `claude-opus-5`（effort `low`，兼顧速度），可用環境變數 `VOICE_MODEL` 覆寫。
理由：要同時對人物、習慣、相對日期做推理，Haiku 錯誤率明顯較高；一次解析成本約 NT$1 上下，家用頻率可忽略。
啟用 server-side fallback（`fallbacks: "default"`），模型婉拒時自動改由其他模型處理。

## 不做（看回饋）
- 多輪對話追問（目前用面板一次列出，使用者在表單直接補）。
- 一句話多個行程。

## 實作備註（2026-10-03）

- 解析核心抽到 `src/lib/voice/parse-event.ts`（schema、習慣摘要、提示詞），route 只負責驗證、呼叫與收斂。
- 「現在時間」放在使用者訊息，系統提示詞（人物＋習慣，約 1 萬 token）標記快取：連續使用時第二次起讀快取。
- 以真實資料實測：「下週二哥哥桌球」補上郭老師、18:15–19:15、地點、標籤並標示依習慣；
  「看林醫師要司機」→ 標出林醫師不在清單、詢問地點；「每週四鋼琴課到十二月底」→ weekly [4]、到 12/31；搜尋句正確判斷。
  速度：首次約 14 秒（schema 首次編譯，之後快取 24 小時），之後約 2.5–7 秒。
